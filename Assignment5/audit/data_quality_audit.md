# Assignment 5 — Synthetic Data Quality Audit

## 1. Capability Under Review

**Bounded capability:** Employee-assisted routing, escalation, and human-review support for web-submitted credit-card billing disputes.

**Scoped development cohort:**
- Product: Credit card
- Issue: Billing disputes
- Submitted via: Web
- Development cases: 653

The purpose of this audit is to determine whether the Development Dataset provides credible evidence for a bounded proof of concept, and to identify limitations that must remain visible.

---

## 2. Proposed Input / Target Boundary

### Primary Model Input

| Field | Role | Rationale |
|---|---|---|
| `consumer_complaint_narrative` | Model input | Contains the customer's complaint description and is the primary unstructured evidence available at intake |

### Target / Reference Outputs

| Field | Role |
|---|---|
| `routing_destination` | Target / reference output |
| `escalation_required` | Target / reference output |
| `human_review_required` | Target / reference output |
| `recommended_next_action` | Downstream reference / operational output |
| `fraud_indicator` | Reference / evaluator label |

### Fields Excluded from Predictive Input

The following fields should not be used as predictive inputs when they represent the target, a direct surrogate for the target, evaluator metadata, or information that could create leakage:

- `routing_destination`
- `escalation_required`
- `human_review_required`
- `recommended_next_action`
- `fraud_indicator`
- `label_status`
- `label_confidence`
- `special_case_flags`

The boundary is intended to prevent the model from learning the answer from labels or derived operational fields instead of using the complaint narrative.

## 3. Data Quality Findings

### Finding 1 — Course-created operating labels are not bank ground truth

The dataset documentation states that the original product/issue fields are retained from source complaint data, while the course operating labels are instructor-created synthetic labels generated by deterministic rules for instructional PoC testing.

**Why this matters:**  
Agreement with the operating labels cannot be interpreted as proof of real-world bank routing performance. The labels are suitable as instructional reference labels, but they should not be treated as verified production ground truth.

**Severity:** High

**Control:**  
Use the labels as reference/evaluation evidence only. Keep the synthetic-label provenance visible in the Data Card and final interpretation.

---

### Finding 2 — Label ambiguity is substantial

Within the 653-case scoped cohort:

| `label_status` | Cases | Share |
|---|---:|---:|
| Clear | 401 | 61.4% |
| Judgment Required | 237 | 36.3% |
| Insufficient Evidence | 15 | 2.3% |
| **Non-clear total** | **252** | **38.6%** |

Approximately 38.6% of the scoped cases are therefore not classified as clearly resolved.

**Why this matters:**  
A simple aggregate accuracy result could hide substantial uncertainty in the reference labels. Cases requiring judgment or containing insufficient evidence should not be interpreted in the same way as clear cases.

**Severity:** High

**Control:**  
Report results separately by label status and avoid presenting a single aggregate score as definitive evidence.

---

### Finding 3 — Target and surrogate leakage risk

Several operating fields are strongly aligned with one another.

Within the scoped cohort:

- All 286 cases with `escalation_required = Yes` also have `human_review_required = Yes`.
- `fraud_indicator` is strongly aligned with routing: all 140 cases routed to Card Fraud & Security have `fraud_indicator = Yes`.

**Why this matters:**  
If these fields are supplied to a model as inputs, the model could infer the target from a synthetic target or a direct surrogate rather than from the complaint narrative. This would create false confidence.

**Severity:** High

**Control:**  
Enforce an explicit input/target boundary. Target and direct-surrogate fields must be excluded from predictive inputs and reserved for evaluation/reference use.

---

### Finding 4 — No low-urgency coverage in the scoped cohort

The scoped cohort contains:

| `urgency_level` | Cases |
|---|---:|
| Low | 0 |
| Medium | 381 |
| High | 171 |
| Critical | 101 |

There are no Low-urgency cases in the scoped cohort.

**Why this matters:**  
The development data provide no evidence about how the proposed capability would behave on low-urgency complaints. Results should therefore not be generalized across the full urgency spectrum.

**Severity:** Medium–High

**Control:**  
Treat low-urgency performance as untested. Additional representative data would be required before making claims about that segment.

---

### Finding 5 — `sub_product` and `sub_issue` are unavailable in the scoped cohort

For all 653 cases in the scoped cohort, `sub_product` and `sub_issue` do not provide usable populated coverage.

**Why this matters:**  
These fields cannot currently contribute reliable information to the proposed routing capability within the scoped cohort. Their presence in the schema should not be mistaken for usable feature coverage.

**Severity:** Medium

**Control:**  
Exclude these fields from the current predictive input design unless populated, representative data become available.

## 4. Targeted Case Inspection

The audit should pay particular attention to cases where label ambiguity or narrative quality may affect evaluation.

### Case: DEV-02350

The case involves a repeated/duplicate credit-card payment issue. The operating labels identify the case as requiring judgment, with a very long/multi-issue narrative.

**Audit relevance:**  
This type of case tests whether a routing system can handle multiple issues and lengthy narratives without assuming that a single complaint maps cleanly to one operational category.

### Case: DEV-02430

The complaint is very short and provides limited evidence about a minimum-payment increase.

The operating label is marked as insufficient evidence with low confidence.

**Audit relevance:**  
This is an important boundary case because the narrative may not contain enough information to support a confident routing decision.

### Case: DEV-05587

The complaint contains a more detailed description involving an online purchase, damaged merchandise, a refund issue, and a disputed charge.

The case is marked as clear with high confidence and requires human review.

**Audit relevance:**  
This provides a contrasting case where the narrative contains substantially more information and the reference labeling is more confident.

## 5. Overall Data-Fitness Judgment

### Judgment: FIT WITH CONTROLS / LIMITATIONS

The Development Dataset is suitable for a **bounded instructional PoC**, but it is not sufficient to support production-level claims about bank routing performance.

The strongest constraints are:

1. The operating labels are synthetic course-created labels rather than bank ground truth.
2. A substantial share of the scoped cases require judgment or contain insufficient evidence.
3. Target and surrogate leakage is possible unless the input/target boundary is explicitly enforced.
4. The scoped cohort has no Low-urgency cases.
5. `sub_product` and `sub_issue` provide no usable coverage in the scoped cohort.

The dataset can therefore support controlled development and evaluation of the bounded capability, provided that the team explicitly documents these limitations and prevents leakage.

## 9. Independent Professional Judgment

The Development Dataset is credible enough for a bounded PoC when used with explicit controls, but it should not be treated as production-quality evidence.

The limitation that most constrains the conclusion is the distinction between **synthetic instructional operating labels and verified bank ground truth**. This means that even a strong model-to-label agreement would primarily demonstrate consistency with the course labeling scheme, not proven operational correctness in a real banking environment.
